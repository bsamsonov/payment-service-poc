# Lane `db` — data model and migration safety

Facts: `facts.md` (changed files, migrations on the base branch, squawk). Project rules: `context.md`
("Schema conventions"), ADRs in `adr/`, the spec and design in `spec/`. A rule written there and broken here is
`drift`; a choice no document settles is `needs-decision`.

## Migration safety
- DB-1 A migration that exists on the base branch is never edited, renamed or deleted (Flyway checksum, RC-12).
  A fix is a new migration. Migrations added by this PR may still change freely.
- DB-2 Versions are sequential and do not collide with other open branches; `R__` only for re-creatable objects.
- DB-3 Changes to tables that already hold data follow expand/contract: a new `NOT NULL` column in steps (add,
  backfill, `SET NOT NULL` via `CHECK … NOT VALID` + `VALIDATE`); new `CHECK`/FK on a large table `NOT VALID` first;
  index `CONCURRENTLY` in its own non-transactional migration; rename/drop over two releases. For `CREATE TABLE` and
  indexes on a table created in the same migration, squawk's lock and timeout rules are not findings.
- DB-4 What cannot be undone is named: dropped data, rows of append-only tables, enum values stored in journals.

## Data model
- DB-5 What kind of table is it (state, history/journal, reference, queue, cache)? A journal stores the change, not
  a snapshot of the entity; one source of truth for every value.
- DB-6 One table, one entity: conditional `CHECK`s of the form "if type X then columns A, B are set" are two entities
  in one table. Rules of one entity ("failure code only when `FAILED`") are fine.
- DB-7 No derived or duplicated values without a constraint that ties them to their source.
- DB-8 Code values follow the project convention (reference table `code` PK + FK, not `CHECK` lists or `ENUM`); the
  same list repeated in several constraints is always a finding; only values the current spec uses.
- DB-9 Columns or enum values "for the future" that the current spec never sets: remove (cheap to add later,
  impossible to remove from append-only data).
- DB-10 Keys: every table has a named PK; identifiers are generated by the application (UUIDv7, ADR-0007);
  uniqueness that a planned spec will have to break (retries, refunds, multiple attempts) is a finding.
- DB-11 Types: `text` with a length `CHECK` where length is a rule, `timestamptz`, money as `bigint` minor units;
  every constraint has a meaningful name (later migrations refer to it).
- DB-12 Every index serves a read path named in the spec; no read path without an index; no duplicate indexes. An FK
  to a reference table needs no index; an FK to an entity does when the parent is deleted or read through it.
- DB-13 Append-only tables, retention and personal data: no PII in append-only rows; retention decided before data
  exists (time partitioning if rows are ever deleted); `jsonb` only with a stated shape and a `jsonb_typeof` check.

## Module ownership
- DB-14 Every table belongs to exactly one module (`boundaries` lane: module = first package segment before the
  layer). Only that module writes it; migrations are named or grouped so the owner is visible.
- DB-15 Foreign keys between tables of different modules couple the modules: allowed only when an ADR or the design
  says so; otherwise the reference is an id column without FK.
