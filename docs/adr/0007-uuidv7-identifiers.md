# 0007. UUIDv7 identifiers generated in the application

- Status: Accepted
- Date: 2026-10-07

## Context and problem
Payments, journal events and rejected requests need primary keys. Payment ids are public (URLs, provider metadata,
logs), so they must not be guessable or reveal business volume. The tables are append-heavy, so keys should keep
B-tree inserts local. The domain layer creates `Payment` and `PaymentEvent` objects and must not depend on JPA or
Hibernate (ArchUnit). The database is PostgreSQL 17, which has no built-in UUIDv7 function (it arrives in 18), and
JDK 25 has no UUIDv7 factory (`UUID.randomUUID()` is version 4).

## Considered options
1. `bigint` sequence (`IDENTITY`).
2. UUIDv4 (`UUID.randomUUID()`).
3. UUIDv7 from Hibernate (`@UuidGenerator(style = VERSION_7)`).
4. UUIDv7 from our own code (~20 lines over `SecureRandom`).
5. UUIDv7 from the `uuid-creator` library, called behind a small domain factory.

## Decision
Option 5: **UUIDv7** (RFC 9562), generated by `com.github.f4b6a3:uuid-creator` behind `PaymentId.newId()` and the
equivalent factories for event and rejected-request ids.

- Versus 1: sequential ids are enumerable and leak volume; the id is known only after an insert.
- Versus 2: random v4 keys scatter inserts across the index; v7 is time-ordered and still has 74 random bits,
  enough to be unguessable and collision-free at our scale.
- Versus 3: the id would exist only after persisting through JPA, while the domain needs it at creation (events,
  logs, the provider call) and must stay free of Hibernate.
- Versus 4: monotonicity within a millisecond and clock handling are easy to get subtly wrong; a small, widely used,
  dependency-free library is cheaper than owning that code.

## Consequences
- Positive: ids are created in the domain without a database round trip; index locality close to a sequence;
  ids sort roughly by creation time, which helps when reading journals.
- Negative: one more runtime dependency; the id embeds the creation time with millisecond precision (acceptable:
  `created_at` is returned by the API anyway).
- Follow-up: when the database moves to PostgreSQL 18 or the JDK gains a UUIDv7 factory, the library can be dropped
  without changing stored data.
