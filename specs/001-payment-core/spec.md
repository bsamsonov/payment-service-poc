# 001. Payment core

## Context
Internal services (e.g. `order-service`) charge a customer's payment method through our REST API. This spec builds the
core: the payment domain and its state machine, the append-only audit journal, persistence, `POST /payments` and the
read endpoints, behind a provider port served by a deterministic **fake provider**. Stripe (003), idempotency (002),
security (004), webhooks (005), refunds (006) and the reconciler (007) plug into this core later.

## Scope
- Domain: `Payment`, `Money(long minor units, Currency)`, currency allow-list (v1: USD, 2 decimals), UUIDv7 ids generated
  by the application.
- Full forward-only state machine `PENDING → PROCESSING → SUCCEEDED/FAILED → PARTIALLY_REFUNDED/REFUNDED`, applied by
  one status-applying component used by every transition source.
- Provider port with four outcomes (see Flow) and a fake adapter selected by `payments.provider=fake`.
- `POST /api/v1/payments`, `GET /api/v1/payments/{id}`, `GET /api/v1/payments?externalReference=`.
- Contract-first `api/openapi.yaml`; interfaces and DTOs generated by openapi-generator (`interfaceOnly`).
- `payments` and `payment_events` tables (Flyway); `payment_events` is append-only, enforced by a database trigger.
- ADR "Audit architecture".

## Non-goals
- `Idempotency-Key`: a repeated `POST` creates a new payment (002).
- Authentication, `client_id`, ownership checks, `actor_id`, `created_by` (004). Read auditing (`AUDIT` logger).
- Real Stripe calls, retries, timeouts, circuit breaker and `503` (003).
- Resolving `PROCESSING`: in 001 a payment with an unknown outcome stays `PROCESSING` until webhooks (005) or the
  reconciler (007) exist. Known limitation.
- Refund API (006); refund statuses exist only in the domain state machine.
- Separate database roles (`payment_owner` for Flyway, `payment_app` without `UPDATE/DELETE`/DDL) — described in the
  ADR as the production option. Hash-chained (tamper-evident) audit records.
- Pagination and filters on the list; listing without `externalReference`; business deduplication by
  `externalReference`.

## Flow
1. Validate the request (`400`/`422`); no payment is created on validation failure.
2. **Tx 1**: create the payment in `PENDING` + event `PAYMENT_CREATED`; commit.
3. Call the provider **outside any transaction**. The outcome is one of:

   | Outcome | Meaning | New status | Response |
   |---|---|---|---|
   | `SUCCEEDED` | charged | `SUCCEEDED` | `201` |
   | `DECLINED(code)` | definite refusal: bank decline, 3DS required, invalid payment method | `FAILED` | `402` |
   | `REJECTED` | provider definitely did not execute the request (e.g. our credentials/request were refused) | `FAILED`, `provider_error` | `502` |
   | `UNKNOWN` | timeout, connection loss, `5xx` — money may have moved | `PROCESSING` | `202` |

4. **Tx 2**: apply the status through the status applier + event `STATUS_CHANGED`; commit; respond.

Mapping of real provider HTTP codes to outcomes is defined in spec 003 (`502/503/504` are `UNKNOWN`, not refusals).

Fake provider, by `paymentMethodId` (same ids as Stripe test payment methods where they exist):

| `paymentMethodId` | Outcome |
|---|---|
| `pm_card_visa` (and any other valid id not listed) | `SUCCEEDED` |
| `pm_card_chargeDeclined` | `DECLINED(card_declined)` |
| `pm_card_chargeDeclinedInsufficientFunds` | `DECLINED(insufficient_funds)` |
| `pm_card_authenticationRequired` | `DECLINED(authentication_required)` |
| `pm_fake_invalid` | `DECLINED(invalid_payment_method)` |
| `pm_fake_provider_error` | `REJECTED` |
| `pm_fake_timeout` | `UNKNOWN` |

## Acceptance criteria
- **AC-1** Given a valid request with `pm_card_visa`, when `POST /payments`, then `201`, `Location: /api/v1/payments/{id}`,
  body with `status=SUCCEEDED`, `refundedAmount=0`; the journal holds `PAYMENT_CREATED` and `STATUS_CHANGED`
  (`PENDING → SUCCEEDED`).
- **AC-2** Given a declining payment method (`card_declined`, `insufficient_funds`, `authentication_required`,
  `invalid_payment_method`), when `POST /payments`, then `402` Problem `payment-declined` with `paymentId`, `failure`
  and `Location`; the payment is `FAILED` with that `failure.code` and a message from our fixed dictionary.
- **AC-3** Given `pm_fake_provider_error`, when `POST /payments`, then `502` Problem `provider-error` with `paymentId`;
  the payment is `FAILED` with `failure.code=provider_error`; an ERROR log line is written.
- **AC-4** Given `pm_fake_timeout`, when `POST /payments`, then `202` with `Location` and body `status=PROCESSING`.
- **AC-5** Given a syntactically invalid request (malformed JSON, missing/unknown field, wrong type, length or pattern
  violation, lowercase currency), when `POST /payments`, then `400` Problem `validation-error` listing **all** field
  errors in `errors[{field, message}]`; no payment is created.
- **AC-6** Given amount `< 50` cents, amount with more than 8 digits, or a currency outside the allow-list, when
  `POST /payments`, then `422` Problem `business-rule-violation` with `errors`; no payment is created.
- **AC-7** Given an existing payment, when `GET /payments/{id}`, then `200` with the payment body (no `paymentMethodId`).
- **AC-8** Given an unknown or malformed id, when `GET /payments/{id}`, then `404` Problem `payment-not-found`.
- **AC-9** Given payments with the same `externalReference`, when `GET /payments?externalReference=…`, then `200` with at
  most 20 of them, newest first; no match → `200 []`; parameter missing → `400`.
- **AC-10** Given a payment in a status, when a transition that is not forward (backward, or out of a terminal state) is
  applied, then the status is unchanged, no error is raised to the caller, and an event `TRANSITION_REJECTED` is
  recorded. Applying the current status again is a no-op without an event.
- **AC-11** Given any status change, then exactly one `payment_events` row is written in the same transaction, with
  consecutive `sequence_no` per payment and a snapshot of `status`, `amount`, `currency`, `refunded_amount`; if the
  event insert fails, the status change is rolled back.
- **AC-12** Given rows in `payment_events`, when `UPDATE`, `DELETE` or `TRUNCATE` is executed, then the database rejects
  it.
- **AC-13** Given the provider is called, then the `PENDING` payment is already committed and no database transaction
  is open during the call.
- **AC-14** Given two concurrent status changes of one payment, then neither is lost: the optimistic-lock loser re-reads
  and re-applies its transition under AC-10 rules.

## Errors
| Situation | HTTP status | Problem `type` |
|---|---|---|
| Malformed JSON, missing/unknown field, type/length/pattern error | 400 | `/problems/validation-error` |
| `externalReference` missing on list | 400 | `/problems/validation-error` |
| Amount out of bounds, currency not allowed | 422 | `/problems/business-rule-violation` |
| Declined by provider | 402 | `/problems/payment-declined` |
| Provider rejected the request | 502 | `/problems/provider-error` |
| Payment not found / malformed id | 404 | `/problems/payment-not-found` |

`402` and `502` carry `paymentId` and `Location`; `400`/`422` carry `errors[{field, message}]`.

## Non-functional requirements
- Audit: every transition is journaled in the same transaction (AC-11); the journal is append-only (AC-12).
- Logging: one INFO line per status change (`paymentId`, `from → to`, `source`, `reasonCode`); never amounts,
  `description`, `metadata`, `paymentMethodId` or request bodies.
- `failure.message` comes only from our dictionary; provider texts never reach the client.
- p95 < 300 ms excluding the provider (target, not gated).

## API changes
New `api/openapi.yaml`:
- Request: `amount` (integer, minor units), `currency` (ISO 4217, uppercase), `paymentMethodId` (`pm_` + `[A-Za-z0-9_]`,
  ≤ 255), `externalReference` (required, ≤ 100, `[A-Za-z0-9._:-]`), `description` (≤ 500), `metadata` (≤ 10 string
  pairs, key ≤ 40, value ≤ 500). Unknown fields are rejected.
- Payment response: `id`, `amount`, `currency`, `externalReference`, `description`, `metadata`, `status`,
  `refundedAmount`, `failure{code, message}` (only when `FAILED`), `createdAt`, `updatedAt`. camelCase, ISO-8601 UTC
  (`Z`), absent optional fields omitted.
- `failure.code` ∈ `card_declined`, `insufficient_funds`, `authentication_required`, `invalid_payment_method`,
  `provider_error`.

## Data changes
- `payments`: `id uuid` PK, `amount bigint` (> 0), `currency char(3)`, `payment_method_id`, `external_reference`
  (indexed with `created_at`), `description`, `metadata jsonb`, `status`, `refunded_amount bigint` (0 ≤ x ≤ amount),
  `failure_code`, `created_at`, `updated_at` (Spring Data auditing), `version` (optimistic lock).
- `payment_events`: `id uuid` PK (UUIDv7), `payment_id` FK **without cascade**, `sequence_no` (unique per payment),
  `event_type` (`PAYMENT_CREATED`, `STATUS_CHANGED`, `TRANSITION_REJECTED`), `from_status`, `to_status`, `actor_type`
  (`CLIENT`, `PROVIDER`, `SYSTEM`, `OPERATOR`), `actor_id` (null until 004), `source` (`API`, `PROVIDER_RESPONSE`,
  `WEBHOOK`, `RECONCILER`, `REFUND`), `reason_code`, `provider_code`, snapshot `amount`/`currency`/`refunded_amount`,
  `request_id`, `provider_request_id`, `provider_event_id`, `provider_http_status`, `provider_attempts`,
  `provider_duration_ms`, `occurred_at`, `recorded_at`, `details jsonb`. No card data, `description`, `metadata` or
  request bodies.
- Trigger: `BEFORE UPDATE OR DELETE … FOR EACH ROW` and `BEFORE TRUNCATE … FOR EACH STATEMENT` raise SQLSTATE `42501`.
  The JPA entity is `@Immutable`; the repository has no delete methods.

## Open questions
1. `request_id`: accept the caller's `X-Request-Id` (validated, ≤ 64 chars) or always generate our own (and return it
   in the response header)? Recommendation: accept if valid, otherwise generate; always echo back.
2. `TRANSITION_REJECTED` rows could grow under webhook storms (005). Keep journaling them, or log only? Recommendation:
   journal them in 001; revisit in 005.
